# 01 — Factibilidad FLoCI y contrato entre servicios

> **Retirado en etapa 05 (2026-11):** los GET de bytes `GET /documentos/{presupuesto|apus|cronograma|especificaciones-tecnicas}/{id}`, sus servicios de descarga y los *writers* XLSX/PDF/MSPDI de Core ya no existen; la descarga es `POST …/exportaciones` + ticket de Core. Este documento conserva el estado histórico; ver [etapa 05](05-retiro-descargas-legadas.md).

**Objetivo:** cerrar primero las decisiones que podrían invalidar el flujo Cliente → Core → Documentos → S3 → Cliente, sin modificar todavía los servicios de producción.

## Acciones de esta etapa

1. Levantar la línea base de las siete rutas documentales y del frontend: autorización/404 por recurso ajeno, preflight/409, formatos y contenido, `Content-Disposition`, stale y auditoría. Presupuesto/APU **no** registran hoy `DOCUMENTO_EXPORTADO`; especificaciones y cronograma sí. Releer resources y tests reales antes de declarar paridad.
2. Hacer una **prueba acotada de FLoCI 2.4.0** en entorno aislado: se probaron S3, host firmado, expiración y privacidad desde el host con AWS CLI y credenciales ficticias (evidencia abajo). **No** se probaron SDK Java, credenciales de pod, navegador desplegado, TLS/ALB ni equivalencia AWS: quedan como verificaciones obligatorias de implementación/despliegue en planes 02/03. No tocar `propuestas-backups`.
3. **Decisión cerrada:** URL temporal de Core con proxy a S3 privado y ticket de un solo uso. La prueba local no permite aprobar S3 directo desde el navegador; Core no expone ni reescribe una URL S3. El POST sí usa JWT; el GET del ticket usa una capacidad bearer que hay que proteger como secreto.
4. Diseñar el contrato interno Core → Documentos como DTO versionado y autosuficiente por formato: identidad pública UUIDv7 (nunca PK BIGINT), tipo/opciones, datos proyectados, orden, precisión `BigDecimal` sin `double`, avisos y metadatos de origen. Definir límites de tamaño, autenticación entre servicios, rechazo de versiones incompatibles e identidad de operación para reintentos; Documentos no toma decisiones de propiedad ni recalcula totales de negocio.
5. Acordar el contrato de resultado: referencia opaca del objeto, MIME, nombre seguro, bytes/checksum, correlación, ticket de Core válido **5 minutos una sola vez** y retención privada del objeto de **24 horas**. Documentos no firma URLs públicas; Core conserva la referencia privada y emite el ticket; no se exponen credenciales ni host S3.
6. Identificar cambios necesarios en `thesis-docs` (contrato API, arquitectura, calidad y manual de despliegue). Acordarlos **antes de implementar** una conducta que contradiga ese canon; estos planes no sustituyen la fuente normativa.

## Entregables / puerta para el plan 02

- **Cumplido por alternativa fundamentada:** la prueba S3 local se registró, pero no demostró acceso de navegador en EKS; se eligió la URL temporal de Core con proxy a objeto S3 privado, no una URL S3 pública. La prueba de navegador/Pod Identity sigue siendo puerta del plan 03.
- **Cumplido como diseño:** esquema interno de request/response y matriz de formatos/datos/errores; contrato público objetivo reconciliado en `thesis-docs`, con compatibilidad de los GET de bytes durante la transición. No se afirma implementación.
- **Cumplido como decisión de contrato:** ticket de un solo uso y 5 minutos; objeto privado 24 horas; fallo de subida/auditoría sin éxito, operación idempotente por clave y evento solo donde existe hoy. La limpieza efectiva, consumo atómico de tickets y aislamiento de servicios deberán probarse en planes 02/03 antes de entregar al usuario.

## Fuera de esta etapa

No separar Gradle todavía ni migrar cronograma. Su garantía de bloqueo se resolverá expresamente en el plan 04.

## Evidencia y decisiones (sin implementación de servicios)

### Revisión inicial sin entorno; prueba S3 posterior acotada

- **Historial de la revisión anterior:** `docker image inspect floci/floci:2.3.0` devolvió «No such image» y `curl http://127.0.0.1:4566/` devolvió «Failed to connect» (HTTP `000`). Luego el solicitante instaló FLoCI y cambió el objetivo de esta etapa a **2.4.0**. Esos resultados previos no describen el estado actual ni prueban fallos de S3.
- El [manual, introducción](../../../thesis-docs/manual-despliegue-floci/capitulos/01-introduccion.tex) registra una **ejecución integral histórica con FLoCI 2.3.0**; la nueva comprobación 2.4.0 es solo de S3, no de toda la infraestructura. La [infraestructura](../../../thesis-docs/manual-despliegue-floci/capitulos/04-infraestructura.tex) declara solo `propuestas-backups` para respaldos, no un bucket de documentos. La [aplicación](../../../thesis-docs/manual-despliegue-floci/capitulos/07-aplicacion.tex) sirve `/api` por Traefik hacia una única API y usa HTTP público `:8080` en la ejecución histórica.
- **Puerta todavía no superada:** la prueba local 2.4.0 descrita abajo no comprueba acceso desde un navegador de la topología FLoCI/EKS, Pod Identity, AWS SDK Java, compatibilidad TLS/ALB ni cumplimiento real de políticas AWS. SigV4 firma el `Host`: sustituir en una URL firmada el DNS interno `floci:4566` por un host público no es una solución.

### Línea base de conducta que hay que preservar

| Familia | Contrato HTTP vigente y captura | Auditoría vigente |
|---|---|---|
| Presupuesto | `GET /documentos/presupuesto/{id}/preflight` y `GET /documentos/presupuesto/{id}`; XLSX/PDF, `?formato=` obligatorio; PDF acepta `orientacion=vertical|horizontal`. Captura de solo lectura `REQUIRES_NEW`, `REPEATABLE READ`; writer fuera de transacción. | Sin `DOCUMENTO_EXPORTADO`. |
| APU | `GET /documentos/apus/{id}/preflight` y `GET /documentos/apus/{id}`; XLSX/PDF; XLSX acepta `layout=pestanas|apilado`. Misma captura y render fuera de transacción. | Sin `DOCUMENTO_EXPORTADO`. |
| Especificaciones | `GET /documentos/especificaciones-tecnicas/{presupuestoId}`; DOCX, `formato=docx` opcional y títulos opcionales. Lectura, generación y evento comparten transacción. | `DOCUMENTO_EXPORTADO` tras bytes generados. |
| Cronograma | `GET /documentos/cronograma/{presupuestoId}/preflight` y `GET /documentos/cronograma/{presupuestoId}`; XLSX/PDF/MSPDI XML; PDF tiene opción `papel`; preflight y generación usan pipeline distinto. Bloqueo de presupuesto hasta bytes materializados. | `DOCUMENTO_EXPORTADO` tras bytes generados. |

Los siete paths son relativos: el [contrato canónico](../../../thesis-docs/plan/architecture/07-api-contract.md) fija prefijo `/api/v1`. Los resources limitan por propietario (recurso ajeno → 404), hacen preflight antes de entregar bytes y devuelven 409 tipado en bloqueos; conservar advertencias stale y demás opciones por formato. El [frontend](../../../thesis-front-react/src/features/exportar/hooks/useExportar.ts) actualmente descarga `Blob` y usa `URL.createObjectURL`, no una referencia S3. Referencias para lectura de código: [`OpcionesDocumento`](../../src/main/java/ec/uce/propuestas/documento/exportacion/OpcionesDocumento.java), [`SnapshotDocumento`](../../src/main/java/ec/uce/propuestas/documento/exportacion/SnapshotDocumento.java), [`DocumentoResource`](../../src/main/java/ec/uce/propuestas/documento/DocumentoResource.java), [`CronogramaDocumentoResource`](../../src/main/java/ec/uce/propuestas/documento/CronogramaDocumentoResource.java).

**Discrepancias canónicas reconciliadas como diseño, no como implementación:** el [contrato API §8](../../../thesis-docs/plan/architecture/07-api-contract.md) identifica el antiguo `GET /documentos/apu/{apuId}` como no implementado, describe los GET actuales de bytes y sus excepciones de auditoría/409, y separa las rutas **POST/JSON objetivo** del GET antiguo. El frontend sigue descargando `Blob`; su migración y las pruebas públicas de los nuevos endpoints pertenecen a los siguientes planes.

### Contratos de diseño acordados; no API implementada

**Decisión de producto cerrada, implementación pendiente:** el solicitante eligió una nueva operación **POST síncrona que crea el objeto y devuelve JSON con URL temporal de Core**; Core sirve los bytes mediante proxy desde S3 privado, no publica ni reescribe una URL S3 presignada. La URL vale **5 minutos y se usa una vez**; el objeto privado permanece **24 horas**. Son plazos distintos. Los GET actuales de bytes y preflight permanecen durante la transición. El [contrato canónico §8](../../../thesis-docs/plan/architecture/07-api-contract.md) ahora distingue rutas vigentes de rutas objetivo **no implementadas**.

### Contrato público objetivo y compatibilidad

| Familia (`{presupuestoId}` UUIDv7, salvo el ticket opaco) | POST de generación objetivo | Opciones admitidas en JSON; GET anterior se conserva |
|---|---|---|
| APU del presupuesto | `/documentos/apus/{presupuestoId}/exportaciones` | `formato=xlsx|pdf`; `layout=pestanas|apilado` solo XLSX |
| Presupuesto | `/documentos/presupuesto/{presupuestoId}/exportaciones` | `formato=xlsx|pdf`; `orientacion=vertical|horizontal` solo PDF |
| Especificaciones | `/documentos/especificaciones-tecnicas/{presupuestoId}/exportaciones` | `formato=docx`; `titulo1`, `titulo2` opcionales |
| Cronograma | `/documentos/cronograma/{presupuestoId}/exportaciones` | `formato=xlsx|pdf|mspdi`; `papel=a4|a3` solo PDF; **implementación diferida al plan 04** por bloqueo temporal |

Todos usan prefijo `/api/v1` y `Idempotency-Key` UUIDv7 obligatorio. `DocumentoExportarRequest` normaliza solo opciones válidas y Core valida autoría, preflight, bloqueos y versión antes de enviar datos. `DocumentoExportacionResponse` devuelve `operationId`, URL relativa `/api/v1/documentos/descargas/{ticket}`, `expiresAt` UTC (+5 min), `objectExpiresAt` UTC (+24 h), MIME, nombre seguro, bytes, SHA-256 y warnings. El nuevo GET sirve bytes con cabeceras de adjunto, consume el ticket atómicamente y devuelve 404 si falta, venció o ya se usó. El token en la URL es una **capacidad bearer**, no un GET con JWT: solo el POST protegido puede emitirla. Una lectura fallida exige reemitir ticket mediante el mismo POST autenticado, sin volver a crear el objeto. La URL y el ticket no deben figurar en logs, trazas, analítica ni access logs de Ingress; Core almacena solo hash del ticket, usa HTTPS, `Cache-Control: no-store`, `Referrer-Policy: no-referrer` y no redirige a S3. El navegador solo navega por gesto explícito: un scanner o prefetch puede consumir anticipadamente el ticket y obligar a reemitirlo. Core reclama el ticket con actualización condicional en su base (`consumedAt IS NULL`, vigencia del ticket **y** del objeto), antes del GET S3; en concurrencia solo un GET obtiene bytes y si falla la transferencia no se recicla ese ticket. La documentación no afirma que el proxy o el despliegue estén operativos.

**Core → Documentos (DTO interno v1, diseño):** `{contractVersion: 1, operationId, correlationId, tipo, formato, opciones, presupuestoPublicId, revision, fingerprint, suggestedFilename, payload}`. `payload` es tipado y completo por formato: APU (secciones y filas en orden, precios y totales proyectados), presupuesto (árbol de capítulos/rubros, importes y firmantes), especificaciones (textos y títulos efectivos), cronograma (actividades, períodos, distribución, valorizado y advertencias, una sola revisión consistente). Core calcula los invariantes y decimales exactos con `BigDecimal` serializado como string, nunca `double`; solo cruza UUIDv7 público, no entidades JPA, PK/FK BIGINT, JWT de usuario ni secretos. Documentos valida identidad de servicio, versión, tipo/formato, longitud del request, integridad/fingerprint, estructura y tamaño de salida; no consulta PostgreSQL, no reautoriza propiedad y no recalcula totales de negocio. La identidad de servicio se verifica con JWT dedicado Core→Documentos (`iss=core`, `aud=documentos`, vencimiento máximo 60 s y rol de servicio), distinto del JWT de usuario, más TLS interno y NetworkPolicy; provisión/rotación de claves, límites numéricos y rendimiento con presupuestos grandes se fijan y prueban antes del primer despliegue, no se presuponen por esta etapa. `SnapshotDocumento` es captura interna, no el DTO remoto.

**Documentos → Core (solo tras subida confirmada):** `{contractVersion: 1, operationId, objectRef, sizeBytes, sha256, mediaType, filename, warnings, uploadedAt}`; `objectRef` es opaca y no es URL ni clave pública de bucket. Documentos usa un key privado estable por `operationId` y metadatos de fingerprint: en un retry tras timeout hace `HeadObject` y compara metadatos/checksum antes de volver a subir o devolver la referencia; conflicto → 409, jamás sobrescribe un objeto distinto. Core reserva con unicidad `(usuario, Idempotency-Key)`, hash del request/revisión y estado persistente con lease/fencing: dos peticiones simultáneas con igual clave no renderizan en paralelo (409 `exportacion-en-curso` si todavía está activa); mismo usuario/clave/cuerpo/revisión recupera el objeto sin auditar dos veces y puede emitir nuevo ticket si sigue vigente; clave reutilizada con otro cuerpo o revisión → 409. El marcador único de auditoría por `operationId` se persiste en la misma transacción del evento. `objectExpiresAt` se ancla a `uploadedAt` confirmado después de PUT/HEAD; a partir de ese instante (24 h) Core niega la lectura aunque la limpieza física aún no haya terminado. Un `PutObject` condicional y la recuperación por HEAD/fingerprint/checksum deben probarse en FLoCI antes de prometer una sola copia. Un 5xx de S3 o auditoría no produce éxito ni enlace: el objeto ya subido queda privado y sujeto a limpieza/recuperación por la misma operación, nunca pública y sin prometer «exactamente una vez» sin prueba. Core emite `DOCUMENTO_EXPORTADO` solo para los tipos que hoy lo hacen (especificaciones y cronograma) después de confirmar subida, con deduplicación por `operationId`; presupuesto/APU no adquieren un evento nuevo silenciosamente. Cronograma no se mueve al POST hasta resolver en el plan 04 su bloqueo presupuestario durante generación y la auditoría ante S3.

**Pruebas de contrato obligatorias antes de implementar cada ruta:** 400 UUID/forma inválida, 401 sin JWT en POST, 404 recurso ajeno/inexistente y ticket inválido/usado/vencido, 409 bloqueo/colisión/idempotencia en curso sin generar ni persistir objeto adicional, 200 con JSON y un objeto privado, GET ticket con MIME/nombre/bytes exactos, dos GET concurrentes con un solo ganador, falla S3 posterior al consumo con reemisión autenticada, límites de `uploadedAt`+24 h y ticket ≤5 min, ausencia de URL S3/secretos/PK incluso en access logs, retry con carga incierta y auditoría una sola vez. Rechazos deben dejar objeto y contadores sin cambios. La limpieza de 24 horas, TLS, servicio-a-servicio y Pod Identity requieren verificación funcional en planes 02/03; la prueba S3 local 2.4.0 anterior no los sustituye.

### Estado de la puerta de etapa

**Cerrada como factibilidad y contrato para iniciar el plan 02; no como despliegue funcional.** El usuario eligió URL temporal de Core con proxy privado, ticket de 5 minutos y objeto de 24 horas. Se documentaron la prueba S3 local, DTO y matriz interna, compatibilidad GET y nuevas rutas POST/JSON **planeadas** en `thesis-docs/plan/architecture/07-api-contract.md`; el navegador no necesita acceder directamente al host S3. La prueba local **no** valida SDK/Pod Identity, identidad entre servicios, navegador real, TLS/Ingress, limpieza efectiva ni el proxy: estos son criterios verificables de los planes 02/03 y no se pueden marcar como aprobados por la etapa 01. Cronograma permanece en Core hasta su decisión de consistencia del plan 04. El PDF histórico se dejó pendiente por decisión explícita del usuario; las fuentes `.tex` sí están actualizadas. El plan 02 puede comenzar, pero no se debe publicar ni dar por funcional la descarga sin sus pruebas de implementación y despliegue.

### Ejecución acotada con FLoCI 2.4.0 (solo S3 local)

El solicitante autorizó iniciar FLoCI 2.4.0 ya instalado. Se crearon dos contenedores **propios y aislados** (`floci-stage01`, `floci-stage01-secure`), unidos solo al loopback del host en puertos `14566` y `14567`; no se tocó el contenedor preexistente `floci` ni el bucket `propuestas-backups`. `floci aws version -o json --container ...` devolvió servidor `2.4.0` en ambos; la imagen instalada como `floci/floci:latest` declaró versión OCI `2.4.0` (digest `sha256:5ee85db604c4aa74ac76e07ea5cc83086f37bb472bf3dbb97e34019e48efae9c`). Para reproducir **2.4.0** en otro entorno se debe fijar una imagen de esa versión/digest, no depender de `latest`.

| Prueba (AWS CLI v2 con endpoint explícito local y credenciales ficticias `test`/`test`) | Configuración predeterminada, `127.0.0.1:14566` | `FLOCI_SERVICES_S3_ENFORCE_AUTH=true` y `FLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED=true`, `127.0.0.1:14567` |
|---|---|---|
| `CreateBucket`, upload `PutObject`/`HeadObject` con `Content-Type` y `Content-Disposition` | Éxito; tamaño 17 bytes; `text/plain`; adjunto `contrato.txt` | Éxito; tamaño 16 bytes; `text/plain`; adjunto `private.txt` |
| GET con URL firmada para `127.0.0.1` y TTL de 5 s | HTTP 200 | HTTP 200; una segunda URL de 30 s devolvió el contenido exacto (SHA-256 del GET igual al del texto de prueba, 16 bytes), en formato path-style |
| GET sin firma del mismo objeto | **HTTP 200: inseguro** | **HTTP 403** |
| Cambiar en URL firmada `127.0.0.1` por `localhost` | **HTTP 200: no valida el host** | **HTTP 403** |
| Alterar un carácter de `X-Amz-Signature` | No probado | HTTP 403 |
| GET con la misma URL después de 7 s | HTTP 403 | HTTP 403 |
| Persistencia | `HeadObject` exitoso tras `docker restart` del contenedor propio con volumen `floci-stage01-data` | No comprobada en esta variante sin volumen |

Se usó `aws --endpoint-url http://127.0.0.1:<puerto>` con variables `AWS_CONFIG_FILE=/dev/null`, `AWS_SHARED_CREDENTIALS_FILE=/dev/null`, `AWS_EC2_METADATA_DISABLED=true`, región `us-east-1` y credenciales ficticias, y `curl --noproxy '*'` para GET. Las URL firmadas completas **no se guardaron**. Esta prueba demuestra que los dos controles de seguridad activados **juntos** producen rechazo anónimo y del `Host` alterado en el emulador local; no demuestra que cada control por separado sea suficiente, ni seguridad real de IAM/AWS, ni acceso desde un navegador externo o un pod. La caducidad de una URL no borra el objeto. Fuente: [anexo FLoCI 2.4.0](../../../thesis-docs/manual-despliegue-floci/capitulos/14-anexos.tex).
